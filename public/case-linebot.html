Case Study 03

LINE Bot 通知管理平台

分開測站、群組、成員、權限與通知規則的設定視角，讓註冊、綁定與通知管理不互相打架。

通知管理 權限流程 群組 / 成員 Wireflow 後台系統
專案背景 需求與痛點 設計策略 流程與成果 專案資訊 TOP
01

Context

專案背景

LINE Bot 通知管理平台讓管理處主管、人員與公司 PM 設定異常事件通知、群組、使用者與推播範圍。不同角色需要收到對應的測站、群組或物理量通知，避免訊息過多，也避免漏接重要異常。

難點在於資料關係交錯：測站群組、測站、使用者群組、使用者、權限與物理量彼此相關。從測站群組進入和從成員列表進入時，使用者想完成的任務不同，畫面也需要換一種說法。

02

Needs & Pain Points

通知管理的使用痛點

設定對象、通知範圍與權限彼此交錯，使用者需要先知道自己正在從哪個視角操作。

設定對象容易混淆

測站群組、測站、使用者群組、使用者、權限與物理量彼此相關，使用者容易分不清正在設定的是範圍、對象還是通知項目。

入口視角不同

從測站群組進入，和從群組 / 成員列表進入時，使用者的任務不同，需要明確拆開流程與標題語意。

通知設定容易過載

如果一次顯示太多測站、成員與通知項目，使用者會很難判斷哪些要開、哪些要關。

權限與啟用狀態要清楚

需要用一致的 checkbox、命名與提示文字，讓使用者理解啟用 / 停用、可見範圍與通知對象。

元件一致但流程要分流

不同流程不能混在一起，但表格、列表、搜尋、篩選與保存操作仍要維持一致，讓使用者不用重新學一次。

03

Design Strategy

設計策略

我先用 wireframe / flow 拆解測站、群組、成員、權限與通知規則，並將「測站視角」與「群組成員視角」分成不同入口或 tab。

表格支援搜尋與篩選，啟用狀態以 checkbox 呈現，並透過命名與提示文字補足語意。重點是讓每一步都能回答「我在設定誰、設定哪些通知、會影響哪些對象」。

流程因此拆成兩種視角：從測站或測站群組出發，管理整體通知範圍；從群組或成員列表出發，管理單一人員可接收的通知。兩者沿用相近元件，但入口、標題與提示文字明確區分。

  • 分視角：把測站 / 測站群組與群組 / 成員設定拆成不同入口，避免任務混在一起。
  • 少一點壓力：表格加入搜尋、篩選與 checkbox，避免一次顯示過多通知設定。
  • 說清楚：用命名與提示文字說明目前設定對象、通知範圍與保存結果。
04

Key Flows & Outcomes

主要流程、設計重點與成果

註：部分畫面已去識別化處理，僅用於呈現設計流程、資訊架構與介面結構。

註冊 / 登入 / 綁定

設計重點：把帳號建立、登入與 LINE 綁定拆成連續步驟，並在每一步說明完成狀態。

形成的結果：初次使用者能理解帳號與通知服務的關係，降低進入系統前的設定阻力。

管理全通知設定

設計重點：從測站與通知範圍出發，逐層選擇群組、測站與通知項目。

形成的結果：管理者能從全域視角確認哪些範圍已啟用，不會和個人權限混在一起。

管理某人員設定

設計重點：從成員列表進入，針對單一人員設定可接收的測站、群組與通知項目。

形成的結果：個人通知範圍有清楚入口，管理者能快速確認某位成員會收到什麼。

搜尋 / 篩選 / 啟用

設計重點：以搜尋、篩選、checkbox 與明確保存步驟承接大量通知項目。

形成的結果：使用者可逐項確認啟用狀態，降低漏接異常或通知過載的風險。

05

Project Information

專案資訊

Role

我的角色

負責前期 wireframe / flow、通知設定流程、權限規則、群組 / 使用者管理、元件整理與工程規格溝通。

Users

主要使用者

管理處高層或主管、管理處人員，以及協助設定群組、成員與通知規則的公司內部 PM。

Scope

涵蓋範圍

註冊、登入、綁定、全域通知、個人通知、成員列表、搜尋篩選與權限設定。
